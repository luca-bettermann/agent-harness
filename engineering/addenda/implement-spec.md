## Our additions

- **Tracker:** the spec is the project description and each ticket is an issue, per the tracker mapping named in INSTANCE.
- **Branches:** the integration branch is `project/<slug>` in every repository the project touches. Each issue branch uses the tracker's branch name, the same in every repository, with one worktree per repository under the INSTANCE work root.
- **Landing:** an issue merges directly into the project branch once its light CI jobs pass on the issue branch; heavy jobs run on the project MR. The project lands through one MR per repository into `main`.
- **Knowledge issue:** "Update knowledge" (`ready-for-human`) goes to no implementer; after step 7 it waits for an interactive session with the operator.
- **Sweep:** before step 1 and after step 9, check what agent runs created (worktrees under the INSTANCE work root, their issue branches, and step-2 notes under its scratch root) against the tracker. When the issue is closed (done or canceled), remove each one that is clean and contained in `origin/main` or a `project/*` branch (`git worktree remove`, `git branch -d`, `git push origin --delete`), then run `git worktree prune`. Leave other owners' branches and worktrees; report them, and anything you couldn't remove, to the operator with the reason.
- **Budget:** start a subagent only while the cost units of running subagents stay within the vendor's cap. Tier weights, caps (the coordinator counts) and vendor order come from INSTANCE. Builders run on the INSTANCE default build tier; a higher tier needs a reason stated in the brief. A session that hits a limit leaves its issue in progress for the next session to continue.
