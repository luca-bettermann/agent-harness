---
name: engineering
description: Engineering rules beyond AGENTS. Use for any change to code, tests, CI or configuration, and for reviewing or designing them.
---

- **Requirements** trace to a real goal and its source; "don't build it" is the first option.
- **No replay.** A cancellation preserves uncertain effects and doesn't authorize a replay. A retry only re-establishes a lost connection, with backoff and a log line when the outage starts and when it ends; nothing that acts on hardware or runs a job retries.
- **Operator responsibility.** Software guards the common path and the hazards an operator can't see or stop in time. Rare faults, deliberate operator actions, and anything the hardware e-stop or the robot's own limits cover belong to the operator. A new gate, safety test or fault-handling path names the real scenario, how often it happens, and why the operator can't own it; without that, it isn't built.
- **Gates.** A gate is any condition that refuses a start, stops a run, drops data or marks a device not ready. Only an operator ruling, cited in the commit, or physical safety at the device owner may add one; without that it becomes a question to the operator. Missing, stale or unproven input is reported, as a warning or a record marked incomplete, and never stops work by itself. A gate refuses only the faulty case: its condition reads what the run will actually use, from that value's owner, and a test shows the nearest valid run passing it.
- **Iterate to acceptance.** Prove every acceptance criterion on a development instance, following the proof rule in ci `docs/workflow.md` (located by INSTANCE "Hosting and CI"). A run counts as complete only when its executed tasks match the plan. A proof run ends without warnings: fix each one, accept it on the issue with a reason, or open an issue for it. Review receives only proven work: before requesting it, post the proof of every criterion on the issue and read your own diff against the AGENTS principles and the skills it touches, fixing what you find.
- **Efficiency.** Design for the real data size from the start. A change on a bulk or hot path (export, import, reads across many runs or records, startup, anything a person waits for) states time and memory budgets in its acceptance criteria and measures them on realistic data on a development instance, cold and warm, never in a CI test job. Stream and page instead of loading everything at once, do expensive work once, and show progress for any wait over a second. A measured result over its budget is a defect, not a note.
- **Dependencies between repositories** go only through published versions: a declared compatible range plus an exact lock. A release pins one known set of exact versions.
- **Stop only for open design.** Bring a decision to the operator (in an interactive session through `grilling`) only when it is a new design question that the principles, doctrine and skills don't settle; post it on the issue with a recommendation and keep working on everything that doesn't depend on it. Otherwise decide by them, keep going, and report the decision with the result.
- **Settings** are read once, in one typed settings module per component that holds every default and says what each variable means. Values come from environment variables and an optional `.env` file at one documented path, never found through the working directory; a committed `.env.example` lists every variable. Code never writes settings back.
- **Console and logs.** The console is for people: only what they need, one line per action. A running line ends in `…` and is replaced by its outcome (`✓` done, `✗` failed, `!` warning); bounded work shows a progress bar. Line width never depends on the data: grow by rows, and summarize a variable count into a fixed set of columns. Full detail goes to a log file in the component's data folder, bounded by size rotation; nothing grows without limit. Use the console and logging libraries INSTANCE names, never a hand-written one.
- **Module descriptions.** Every folder that is a module has a `README.md` of about 15 lines at most, holding what the code can't say: the concept, how its files work together, what is out of scope and where that lives, and what it depends on. No file-by-file list. The change that alters a module's responsibility updates its description.
- **CI.** Play the jobs your change needs and wait for their result (AGENTS, Predictable behavior). A project branch receives only work whose required checks are green.
- **Tests.** Each boundary has one shared test harness, built from the real code on both sides and reused by every test that crosses it; a side that can't run in a test is a minimal fake of its published contract. A test that needs a dependency the local environment lacks runs in CI against the real one. Use the smallest real input that still shows the failure; no test job runs a full-scale dataset. A test stays only when its benefit clearly exceeds its cost in code and run time; a job over the installation's time budget gets smaller inputs, never a longer timeout. Golden files change only through a ruled regeneration that names the fields allowed to differ; everything else must still match.
