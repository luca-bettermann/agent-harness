---
name: frontend
description: Browser interface rules. Use for any change to a web UI, and for testing or reviewing one.
---

- **Design before build:** a visible change reaches the operator before it is built: a small mock-up or screenshot (the `prototype` skill builds throwaway ones), iterated until the operator agrees. A change alters only what it names and keeps today's good layouts; a general rule (an ADR, this skill, a principle) that would change an element nobody named is shown to the operator as a before/after, never applied silently. In an autonomous run, post screenshots on the issue as soon as the first version renders, before polishing, and again at the end.
- **Components:** shadcn/ui first. Build a component of your own only where shadcn has none, and keep it in the shared shell, one component per concept for every app. The installation names the shell, its tokens and its README (INSTANCE); read them before building.
- **Tokens:** one token file serves all apps; app stylesheets hold layout only. A component or page never holds a literal colour or font size: use token utilities. The palette has one colour per meaning, and the shadcn names are aliases of it.
- **Quiet UI:** at rest each object is one line: its name, its status and one key value. Few colors, little decoration, dense but calm layouts; small text appears only where it is the content (a failure message, a log tail). References: the Claude and Codex apps, Linear, Vercel, Raycast.
- **Details on demand, one mechanism:** everything beyond the one line opens in place through one expand mechanism for the whole product: hover opens it briefly, a click keeps it open until the next click, and both look the same. No info icon per row, no second mechanism such as a tooltip with detail; a native `title` only reveals a truncated label. No toasts: an outcome shows where the action was taken and stays until the state changes. What the user needs to act safely stays visible: errors, blocking warnings, and units where a value would otherwise be ambiguous.
- **One visual language:** all apps of a product look and behave alike; a difference between two apps is a defect unless a ruling names it.
- **Project UI standards are ADRs:** each project records its concrete UI standards (messages, buttons, markers, colours, panes, lists, switchers, wording) as ADRs in the repository that owns its shared shell, and the installation points there (INSTANCE). Read them before a UI change; a new standard is an ADR, not a line in an app.
- **Conformance gate:** a reviewer who did not build the screens derives a numbered rule list from primary sources only: the project's UI ADRs, this skill and the operator's verbatim comments (coordinating, "Operator words"). It then audits every screenshot of every changed view against each rule. A broken rule goes back to the builder, which fixes the shared component first and the views through it. The audit repeats on the new screenshots. The operator sees screens only at zero broken rules; a rule the reviewer can't settle, or a change to an element nobody named (Design before build), goes to the operator as a question.
- **Times:** store UTC; show the installation's one time zone through one shared formatter, with no UTC on hover. Exports write local time with its offset.
- **Responsive:** engineering's _Efficiency_ holds for every new or changed key screen, with budgets for first content, ready and response to input, measured in the real browser. Lists page by 50 through a server cursor, and search and sort run on the server. Loading shows skeletons, never a blank area. Layouts adapt to the window, from a laptop to a large monitor; phones are out of scope.
- **Verify in the real browser:** walk every affected user journey on the rendered page before handing over. Type checks and screenshots don't show interaction.
