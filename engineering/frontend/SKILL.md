---
name: frontend
description: Browser interface rules. Use for any change to a web UI, and for testing or reviewing one.
---

- **Design before build:** before building a new view or a visible change, show a small mock-up or screenshot (the `prototype` skill builds throwaway ones) and iterate until the operator agrees. In an autonomous run, post screenshots on the issue as soon as the first version renders, before polishing, and again at the end; the operator can't see local files.
- **Components:** shadcn/ui first. Build a component of your own only where shadcn has none, and keep it in the shared shell so every app gets the same one. Help text uses the shadcn Tooltip; a native `title` only reveals a truncated label. The installation names the shell, its tokens and its README (INSTANCE); read them before building.
- **Tokens:** one token file serves all apps; app stylesheets hold layout only. A component or page never holds a literal colour or font size: use token utilities. The palette has one colour per meaning, and the shadcn names are aliases of it (destructive, ring, secondary, accent, input). Blue means running or live only; info is neutral.
- **Quiet UI:** few colors, little decoration, dense but calm layouts. References: the Claude and Codex apps, Linear, Vercel, Raycast. A redesign keeps today's good layouts and changes only what it names.
- **Information on demand:** by default a row or control shows its name and value; help appears below the field while it is hovered or focused, with no info icon per row. No toasts: an outcome shows where the action was taken and stays until the state changes. What the user needs to act safely stays visible: errors, blocking warnings, and units where a value would otherwise be ambiguous.
- **Times:** store UTC; show the installation's one time zone through one shared formatter, with no UTC on hover. Exports write local time with its offset.
- **Responsive:** every view shows content quickly and answers input without a noticeable wait. Each new or changed key screen states time budgets in its acceptance criteria (first content warm and cold, ready, response to input), measured cold and warm in the real browser on the development platform. Never load a whole dataset: lists page by 50 through a server cursor, and search and sort run on the server. Loading shows skeletons, never a blank area. Any wait over 1 s shows progress; a long job shows live progress and Cancel. Layouts adapt to the window, from a laptop to a large monitor; phones are out of scope.
- **Verify in the real browser:** walk every affected user journey on the rendered page before handing over. Type checks and screenshots don't show interaction.
